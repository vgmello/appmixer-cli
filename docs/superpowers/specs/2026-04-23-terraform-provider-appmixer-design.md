# Terraform Provider for Appmixer — Design

**Date:** 2026-04-23
**Status:** Approved via brainstorming; ready for implementation plan
**Related:** `src/commands/provision/` (existing YAML provisioning CLI), `docs/appmixer/api/*.md` (mirrored API reference)

## Overview

Build a Terraform provider, `terraform-provider-appmixer`, that manages an Appmixer tenant's admin-scoped resources declaratively. The provider is aimed at platform operators who run one or more Appmixer tenants and want to bootstrap and reconcile them from CI/CD instead of bespoke YAML + the existing `appmixer-adm provision apply` flow.

The provider will cover seven resource types in its MVP: `appmixer_config`, `appmixer_service_config`, `appmixer_acl`, `appmixer_modifiers`, `appmixer_flow`, `appmixer_account`, and `appmixer_user`. Each supports the full create/read/update/delete lifecycle with drift detection, and `terraform import` from day one so existing tenants can be adopted into state.

### Primary use case

Tenant provisioning in CI/CD. The operator maintains a git repo of HCL modules per tenant (or uses a single module with provider aliases), and `terraform apply` reconciles the tenant against that declared state. The provider replaces the `provision apply` CLI for the three domains that CLI covers (`config`, `service-config`, `acl`) and extends coverage to flows, modifiers, accounts, and admin users.

### Non-goals

- Data sources for read-only endpoints (insights, statistics, integration-categories, unprocessed-messages, people-task). Deferred.
- Resources for `charts`, `user-groups`, `data-stores`, `apps`, `public-files`, `variables`. Deferred (variables have no CRUD API — they live inside flow JSON).
- Flow `stage` lifecycle (start/stop via `/coordinator`). Server-owned; exposed only as a read-only computed attribute.
- Token refresh during long-running applies. Provider logs in once per apply.
- Password-change and account-token-rotation actions. `password` and `account.token` are write-once in MVP; changes require taint + recreate.
- Public Terraform Registry publication. Ship as a binary for `dev_overrides` or a private registry. Registry push is a follow-up.
- OpenAPI spec generation and client codegen. Evaluated and explicitly deferred — a partially wrong spec is worse than no spec.

## Architecture

### Repo

A new repo, `terraform-provider-appmixer`, separate from `appmixer-cli`. Go module `github.com/<org>/terraform-provider-appmixer`. Standard provider layout:

```
.
├── main.go                        # provider entrypoint
├── internal/
│   ├── provider/provider.go       # schema, Configure(), resource registry
│   ├── client/                    # thin HTTP client (auth, request, errors)
│   │   ├── client.go
│   │   ├── auth.go
│   │   └── errors.go
│   └── resource/                  # one file per resource
│       ├── config.go
│       ├── service_config.go
│       ├── acl.go
│       ├── modifiers.go
│       ├── flow.go
│       ├── account.go
│       └── user.go
├── examples/                      # HCL examples per resource (feed tfplugindocs)
├── docs/                          # generated via tfplugindocs
├── .goreleaser.yaml
├── go.mod
└── README.md
```

### Framework

`github.com/hashicorp/terraform-plugin-framework` (the current HashiCorp-recommended SDK; SDKv2 is legacy). Acceptance tests use `github.com/hashicorp/terraform-plugin-testing`. Docs generated by `github.com/hashicorp/terraform-plugin-docs` (`tfplugindocs`).

### Provider configuration

The provider authenticates exactly like the CLI: base URL + username + password, exchanged for a bearer token on start.

```hcl
provider "appmixer" {
  base_url = "https://api.example.appmixer.cloud"  # or APPMIXER_BASE_URL
  username = "admin@example.com"                   # or APPMIXER_USERNAME
  password = var.appmixer_password                 # or APPMIXER_PASSWORD (sensitive)
}
```

`Configure()` does `POST /user/auth`, caches the bearer token in the client instance for the lifetime of the apply, and attaches it to all subsequent requests. Errors in `Configure()` surface as diagnostic errors before any resource runs. No token refresh in MVP.

Multi-tenant setups use standard Terraform provider aliasing:

```hcl
provider "appmixer" { alias = "prod"; base_url = "..."; username = "..."; password = "..." }
provider "appmixer" { alias = "staging"; base_url = "..."; username = "..."; password = "..." }

resource "appmixer_config" "jwt" { provider = appmixer.prod; ... }
```

### HTTP client

Plain `net/http`, JSON-encoded, no third-party HTTP library. Responsibilities:

- Base URL + path joining
- Auth header injection (`Authorization: Bearer <token>`)
- 2xx validation
- JSON decode
- Structured error from non-2xx (status code, body, request path, method)
- No retries — Terraform already retries at the resource layer via diagnostics

Shape mirrors `src/client.ts` from this repo. Generic helpers per verb:

```go
func Get[T any](ctx context.Context, c *Client, path string) (T, error)
func Post[T any](ctx context.Context, c *Client, path string, body any) (T, error)
func Put[T any](ctx context.Context, c *Client, path string, body any) (T, error)
func Delete[T any](ctx context.Context, c *Client, path string) (T, error)
```

## Resource catalog

| TF resource | API | ID | Create | Read | Update | Delete |
|---|---|---|---|---|---|---|
| `appmixer_config` | `/config` | `key` | `POST /config` | `GET /config` + filter | `RequiresReplace` on `value` | `DELETE /config/:key` |
| `appmixer_service_config` | `/service-config` | `service_id` | `POST` | `GET /:id` | `PUT /:id` | `DELETE /:id` |
| `appmixer_acl` | `/acl/:type` | `type` (`components` \| `routes`) | `POST /acl/:type` (full list) | `GET /acl/:type` | `POST /acl/:type` | `POST /acl/:type` with `[]` |
| `appmixer_modifiers` | `/modifiers` | singleton (`"default"`) | `PUT` | `GET` | `PUT` | `DELETE` (destructive — see below) |
| `appmixer_flow` | `/flows` | `flowId` (server-assigned) | `POST` | `GET /:id` | `PUT /:id` | `DELETE /:id` |
| `appmixer_account` | `/accounts` | `accountId` (server-assigned) | `POST` | `GET /accounts` + filter | `PUT /:id` (displayName only) | `DELETE /:id` |
| `appmixer_user` | `/users` | `userId` (server-assigned) | `POST /user` | `GET /users/:id` | `PUT /users/:id` | `DELETE /users/:id` + poll ticket |

### Server-assigned IDs as computed outputs

Every resource with a server-assigned ID exposes it as both the default `id` attribute and a domain-named alias so HCL references read naturally:

- `appmixer_flow.<name>.id` and `.flow_id`
- `appmixer_account.<name>.id` and `.account_id`
- `appmixer_user.<name>.id` and `.user_id`

The aliases are computed read-only attributes populated from the API response on create and hydrated on every read.

### HCL surface sketches

```hcl
resource "appmixer_config" "jwt" {
  key   = "JWTSecret"
  value = var.jwt_secret  # sensitive
}

resource "appmixer_service_config" "google" {
  service_id       = "appmixer:google"
  fields           = { client_id = "..." }
  sensitive_fields = { client_secret = var.google_secret }
}

resource "appmixer_acl" "components" {
  type = "components"
  rules = [
    { role = "admin", resource = "*", action = ["*"], attributes = ["non-private"] },
  ]
}

resource "appmixer_modifiers" "default" {
  categories = { object = { label = "Object", index = 1 } }
  modifiers  = { g_stringify = jsonencode({ name = "stringify", ... }) }
}

resource "appmixer_flow" "onboarding" {
  name          = "Customer Onboarding"
  flow_json     = file("${path.module}/flows/onboarding.json")
  custom_fields = { category = "customer-ops" }
}

resource "appmixer_account" "slack_bot" {
  service      = "appmixer:slack"
  display_name = "Platform Slack Bot"
  token        = jsonencode({ accessToken = var.slack_token, scope = [...] })  # sensitive
}

resource "appmixer_user" "admin_ops" {
  email    = "ops@example.com"
  password = var.ops_initial_password  # sensitive, write-only on create
  scope    = ["admin"]
  metadata = { team = "platform" }
}
```

## Per-resource design details

### `appmixer_config`

No `PUT` on the API — only POST and DELETE. The `value` attribute is marked `RequiresReplace`, so editing it triggers destroy + recreate. Acceptable because config values are typically secrets or tenant-level toggles; a momentary gap during apply is tolerable. `value` is sensitive (may hold `JWTSecret` etc.).

Read fetches the full list from `GET /config` and filters by `key`. A missing key marks the resource for recreation.

### `appmixer_service_config`

Two attributes hold the dynamic fields: `fields` (plain `map(string)`) and `sensitive_fields` (sensitive `map(string)`). On write, both are merged with `serviceId` into a single payload. On read, the server returns the full object; any key present in `sensitive_fields` at apply-start stays there, everything else lands in `fields`. New keys that appear server-side (drift) default to `fields`, and the resulting diff prompts the operator to move them if they are sensitive. Key conflict between the two maps is a plan-time validation error.

### `appmixer_acl`

One resource instance owns the entire rule list for its `type`. `POST /acl/:type` replaces the whole list, matching the TF resource semantics.

Drift detection fetches the list via `GET /acl/:type` and compares to state. To avoid spurious diffs from server-side reordering, rules are normalized on both read and plan by sorting on a canonical composite key: `(role, resource, action[] sorted, attributes[] sorted)`. Destroy posts an empty array, which resets the list to empty (*not* the tenant defaults — document this).

### `appmixer_modifiers`

Singleton — one `appmixer_modifiers.default` per tenant. Attributes: `categories` (map of objects) and `modifiers` (map of objects). `helperFn` is JS source as a string, stored verbatim with no parsing.

`DELETE /modifiers` wipes the tenant's modifiers *including Appmixer's built-in defaults*, not just user additions. Destroy surfaces a warning diagnostic at plan time: `"this will remove all modifiers, including Appmixer defaults — to restore defaults, reapply the resource or let the tenant be reprovisioned"`. No opt-out flag in MVP; a `delete_behavior = "keep_on_destroy"` option can be added later if this proves painful.

### `appmixer_flow`

`flow_json` is a plan-diffable string attribute containing the flow descriptor JSON. Typical authoring path: design the flow in the Appmixer UI, export it, store the JSON next to the HCL, reference with `file()`.

Read behavior:

1. `GET /flows/:id`.
2. Strip volatile server-owned fields: `mtime`, `btime`, `stage`, `userId`, `sharedWith` (matching `src/commands/flows/flows-diff.test.ts` conventions from the CLI).
3. Canonicalize JSON (sort object keys, stable whitespace) before comparing to state.
4. Expose `flow_id` (alias of `id`), `mode`, `started`, and `stage` as computed read-only attributes.

Create returns just `{flowId}`; provider follows up with a GET to hydrate state. Update: `PUT /flows/:id` with `flow` + `name` + `customFields` + `thumbnail`. `forceUpdate=false` always — running-flow guard is the server's job, and operators who truly need to force-update can stop the flow first (via the Appmixer UI or a future tool).

`stage` (`running` / `stopped`) is read-only in this resource. Start/stop is out of scope for MVP.

### `appmixer_account`

`accountId` is server-assigned → computed `account_id` alias plus default `id`. Only `display_name` is updatable; changes to `service`, `token`, or `profile_info` force replace.

`token` is sensitive and write-only. The API does not return tokens on read, so the provider persists the last-written token value in state (not round-tripped against the server) — otherwise every read would register as drift. The trade-off: if the token is rotated out-of-band, state stays stale until the resource is tainted.

Read path validates the account with `POST /accounts/:id/test`. `revoked: true` or an expired token surfaces as a warning diagnostic but does *not* force replace — the operator decides whether to rotate.

Use case is specifically pre-obtained, non-interactive credentials (API keys, service-account tokens, stored OAuth refresh tokens). End-user OAuth flows remain UI-driven and outside Terraform's scope.

### `appmixer_user`

Admin-scoped CRUD under `/users`.

`password` is sensitive and write-only on create. The API never returns it; state persists whatever the HCL set, but plan diffs on `password` are suppressed after create. Changes to `password` in HCL after create do not trigger anything — changing a user's password requires a future action or an out-of-band reset (deferred).

Delete is asynchronous: `DELETE /users/:id` returns a ticket. Provider polls `GET /users/:id/delete-status/:ticket` at 2-second intervals until `status` is `completed` or `failed`. Default timeout is 10 minutes, exposed via standard Terraform resource timeouts:

```hcl
resource "appmixer_user" "x" {
  # ...
  timeouts { delete = "10m" }
}
```

`in-progress` → keep polling. `failed` → error diagnostic including `stepsDone` / `stepsTotal` for context.

### Import semantics

Each resource implements `ImportState` hydrating from a single ID string:

| Resource | Import ID |
|---|---|
| `appmixer_config` | the config key |
| `appmixer_service_config` | the service ID |
| `appmixer_acl` | `components` or `routes` |
| `appmixer_modifiers` | literal `default` |
| `appmixer_flow` | the flow ID |
| `appmixer_account` | the account ID |
| `appmixer_user` | the user ID |

Two known quirks are documented, not bugs:

- **Service-config import**: the provider cannot know which fields were intended as sensitive. Everything lands in `fields`, nothing in `sensitive_fields`. The operator's first plan after import will show the split they want.
- **Account import**: the API does not return tokens, so `token` comes back empty after import. The operator must supply the token in HCL for subsequent applies to succeed.

## Testing strategy

### Unit tests

`internal/client/` — Go tests using `httptest.NewServer` to exercise request/response handling, error decoding, and auth header behavior.

`internal/resource/` — pure-function tests for state-transform helpers: JSON canonicalization for flow, ACL rule sort key, sensitive/non-sensitive merge logic, volatile-field stripping.

Run with `go test ./...`, fast, no external deps.

### Acceptance tests

`terraform-plugin-testing` framework. Each resource gets:

- `TestAcc<Resource>_basic` — create, read (verify state), update, destroy
- `TestAcc<Resource>_import` — create, import by ID, verify state match

Gated behind `TF_ACC=1` so `go test ./...` doesn't spin up the backend.

`TestMain` spawns `test/mock-server.ts` from this repo as a subprocess on a random port, waits for health, sets `APPMIXER_BASE_URL` / `APPMIXER_USERNAME` / `APPMIXER_PASSWORD`, then invokes the test runner. The mock-server source is either vendored into the provider repo or referenced via a git submodule — decided during implementation based on release timing.

### Mock-server coverage gaps

The current `test/mock-server.ts` was built for the CLI's three domains (`config`, `service-config`, `acl`, plus `flows apply`). The provider adds four that need mock-server additions:

- `modifiers` — GET / PUT / DELETE
- `accounts` — full CRUD + `/test`
- `users` — full CRUD with async delete ticket polling
- `flows` — full CRUD with response shape (the CLI currently only exercises `apply`-style paths; verify coverage)

Extending the mock is tracked as part of the MVP deliverable.

### CI

Separate workflows for unit (every PR, no backend) and acceptance (every PR, spins up mock). Release workflow runs both before `goreleaser` is invoked.

## Release and distribution

`goreleaser` with the standard `terraform-provider` config:

- Cross-compile: linux/darwin/windows × amd64/arm64
- GPG-sign checksums with a GitHub Actions OIDC-backed signing key
- Tag `vX.Y.Z` triggers the release workflow

Registry-compatible layout from day one. Docs generated by `tfplugindocs` from schema + `examples/resources/*`. MVP ships as a binary consumable via `dev_overrides` in `~/.terraformrc` or via a private OCI registry. Public Terraform Registry publication is a follow-up once the provider is stable.

`0.x` versioning during MVP; breaking schema changes allowed between minors. Cut `1.0.0` once the seven resources are stable and a real tenant has been adopted through the provider end-to-end.

## Open questions and future work

- **Token refresh.** If the JWT's lifetime is shorter than a long-running apply, we need refresh. Not expected in MVP; revisit if a user reports it.
- **Flow `stage` management.** Start/stop is genuinely useful but has non-trivial async semantics. Add a separate `appmixer_flow_state` resource in v0.2 if demand exists.
- **Password rotation / account token rotation.** Both are blocked on `write-only` semantics. When Terraform's write-only attributes (v1.11+) stabilize across backends we revisit.
- **Data sources.** Insights, statistics, integration-categories, unprocessed-messages, people-task. Add once resources are stable.
- **OpenAPI spec.** Build once, reuse across CLI + provider + future SDKs. Significant upfront cost; out of scope for MVP but worth doing once the provider has shaken out the API's rough edges.
- **Public Registry.** Requires GPG signing key, HashiCorp Registry account, release artifact tweaks. Tackle when external adopters exist.
